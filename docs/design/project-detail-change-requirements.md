# 프로젝트 상세 변경 요구사항

작성일: 2026-09-09
수정일: 2026-09-14

상태: Work #26에서 디자인 문서를 수정하고, Work #29에서 세 프로젝트의 1440/390px Pencil 시안에 반영했다. Work #32에서 문서·저장본·실제 렌더를 대조했으며, 확정한 줄바꿈·도식 배치와 원본 연결을 [컴포넌트 문서](components.md#상세-전용-요소)에 기록했다. 검증 범위와 여섯 렌더는 [검증 기록](../verification/project-detail-pencil.md)에 있다. 후속 Deliverable #34에서 상세 콘텐츠·도식·링크·앵커를 코드에 반영했다. Work #41의 [웹 검증 기록](../verification/project-detail-web.md)에 정적 빌드·브라우저·기존 인쇄 회귀 결과를 남긴다.

프로젝트 상세의 공통 본문 섹션을 정리하고, 외부 링크를 목차 아래 한곳에 모으며, 본문 하단에서 이전·다음 프로젝트를 오갈 수 있게 한다. 적용 대상은 [프로젝트 상세 설계](pages/project-detail.md)와 [Pencil 화면](../pen/portfolio.pen)의 ILOG·Lorekeeper·Matching SSAFY 데스크톱 1440px 및 모바일 390px 시안이다.

## 공통 본문 섹션

2026-09-14 논의에서 세 프로젝트 상세에 아래 네 섹션을 같은 순서로 적용하기로 결정했다. 기존 `담당 범위 / 구현 과정 / 검증과 회고` 구성을 대체하며, 본문에 큰 섹션 제목을 표시하고 개별 사례의 소제목과 구별한다. 데스크톱 목차도 이 네 섹션에 대응시킨다. 모바일은 목차를 숨기되 본문 섹션 제목과 순서를 유지한다.

| 순서 | 섹션          | 참고 원문의 제목       | 담을 내용                                                                              |
| ---- | ------------- | ---------------------- | -------------------------------------------------------------------------------------- |
| 1    | 프로젝트 개요 | Overview               | 서비스의 목적, 주요 기능과 본인의 담당 범위                                            |
| 2    | 아키텍처      | Architecture           | 시스템 구성, 구성 요소의 역할과 연결, 본인이 담당한 부분                               |
| 3    | 문제 해결     | Challenges & Solutions | 문제별 소제목 아래 발생 상황과 해결 과정. 확인된 원인과 선택 근거를 포함한다.          |
| 4    | 결과          | Impact & Results       | 확인한 동작과 검증 범위, 실제 성과와 남은 한계. 기존 회고는 관련 결과와 함께 보존한다. |

참고 자료는 [Dinesh Gaikwad의 Developer Portfolio 상세 페이지](https://dineshgaikwad.vercel.app/projects/portfolio)다. 2026-09-14에 원문 본문과 제목 계층을 확인했고, 사용자가 이 사례의 네 섹션 구성과 섹션 내부의 표현 아이디어를 참고하도록 정했다. 확인 범위는 웹 도구가 제공한 본문 구조이며, 실제 렌더의 크기별 시각 비교는 아직 수행하지 않았다.

프로젝트별 본문 배치와 보강은 에이전트가 기존 자료를 근거로 정한다. 기존에 확인한 사실과 검증 한계는 보존하고, 섹션을 채우기 위해 문제 원인·설계 의도·성과 수치를 만들어 넣지 않는다. 자료로 확인할 수 없는 중요한 사실만 사용자에게 확인한다. 프로젝트별 확정 콘텐츠와 표현은 [상세 설계](pages/project-detail.md)에 기록했다. 이 문서는 합의 이력을 유지하며 실제 반영 결과는 위 검증 기록으로 확인한다.

## 기존 디자인을 유지한 표현 방식

기존 포트폴리오의 디자인 요소를 유지하고, 참고 페이지에서 정보 묶음과 설명 순서의 아이디어를 가져온다. [공통 시각 규칙](foundations.md)의 남색 배경·청록색 강조·글꼴·색상별 역할과 [공통 컴포넌트](components.md)의 목차·링크·기술 태그·본문 스타일을 재사용한다. 데스크톱의 왼쪽 소개와 오른쪽 본문, 모바일의 단일 열 구성을 유지한다.

아래 적용 방향은 원문의 본문 구조를 기존 포트폴리오에 맞춘 설계 기준이다. 원본의 카드 외형·간격·애니메이션을 관찰해 복제한 명세가 아니다.

| 섹션          | 원문에서 확인한 정보 표현                              | 적용 방향                                                                                                                                                         |
| ------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 프로젝트 개요 | 배경 설명, 기술 목록, 기능별 소제목과 목록을 구분한다. | 짧은 서비스 소개 뒤에 주요 기능과 담당 범위를 묶어 배치한다. 주요 기술은 기존 SkillTag 표현을 사용한다.                                                           |
| 아키텍처      | 시스템 흐름과 아키텍처 도식 영역을 별도로 둔다.        | 확인된 구성 요소와 연결을 정적 도식으로 보여 주고 아래에 설명한다. 기존 색·글자·선 스타일로 표현하고, 본인의 담당 범위는 레이블로 구별한다.                       |
| 문제 해결     | 문제별 제목 아래 문제 설명과 해결 설명을 구분한다.     | 사례를 독립된 묶음으로 배치하고 `문제 / 원인 / 해결` 레이블과 짧은 문단으로 읽는 순서를 드러낸다. 확인되지 않은 원인은 추정해 채우지 않는다.                      |
| 결과          | 결과별 핵심 값과 설명을 묶어서 제공한다.               | 확인된 결과의 핵심 문구와 설명을 짝지어 배치한다. 근거가 있는 수치는 강조하고, 수치가 없는 결과는 짧은 문구로 표현한다. 검증 한계와 회고는 관련 결과 아래에 둔다. |

큰 섹션 제목과 사례 소제목의 위계, 섹션 사이 여백, 묶음 사이 구분은 기존 디자인 체계 안에서 정한다. 모바일에서는 도식과 결과 묶음을 본문 폭에 맞춰 세로로 재배치한다. 도식·정보 묶음이 기존 요소만으로 표현되지 않으면 기존 스타일 변수를 사용하는 필요한 요소만 설계한다. 참고 페이지의 성과 수치·프로젝트 문구·AI 기능·새로운 시각 효과는 가져오지 않는다.

디자인 문서 수정 시 기존의 `본문을 도해·근거 카드로 다시 포장하지 않는다`, `제목·날짜·역할·본문만으로 프로젝트를 소개한다` 등 이번 방향과 충돌하는 규칙은 프로젝트 상세에 한정해 정리한다. 확인된 시스템 구조를 설명하는 도식과 실제 서비스 화면 캡처를 구분하며, 임의의 서비스 화면은 만들지 않는다.

## 링크·이동 변경 요구사항

1. 저장소·문서 등 프로젝트를 확인하는 데 필요한 외부 링크를 목차 아래에 여러 개 제공할 수 있는 세로 묶음으로 배치한다. 목적지가 같은 링크는 한 번만 제공하고, 서로 다른 저장소는 역할을 레이블에 표시한다. 실제 주소가 있는 자료만 추가한다.
2. 본문 끝의 `코드에서 확인하기`를 제거한다. Lorekeeper의 하단 `프론트엔드 저장소`는 삭제하지 않고 목차 아래 링크 묶음으로 옮긴다.
3. 하단에 `이전 프로젝트 · 프로젝트명`과 `다음 프로젝트 · 프로젝트명`을 제공한다. ILOG, Lorekeeper, Matching SSAFY 순서를 따르며 첫 항목에는 다음만, 가운데에는 이전·다음, 마지막에는 이전만 표시한다. 양 끝을 순환 연결하지 않는다.
4. 마지막 프로젝트 하단의 `프로젝트 목록으로`를 제거한다. 기존 상단 `포트폴리오로` 링크는 유지한다.
5. 모바일은 상세 목차를 숨기는 기존 설계를 유지하고, 외부 링크 묶음을 프로젝트 소개 아래·본문 앞에 배치한다. 하단 이전·다음 링크는 데스크톱과 동일하게 세로로 배치한다.

| 프로젝트       | 링크 레이블       | 목적지                                                   |
| -------------- | ----------------- | -------------------------------------------------------- |
| ILOG           | GitHub 저장소     | `https://github.com/ju1115/ilog`                         |
| Lorekeeper     | 백엔드 저장소     | `https://github.com/soma-lorekeeper/lorekeeper-backend`  |
| Lorekeeper     | 프론트엔드 저장소 | `https://github.com/soma-lorekeeper/lorekeeper-frontend` |

하단 이동은 다음 표로 정리한다. 이전을 위에, 다음을 아래에 두고 각각 왼쪽·오른쪽 화살표를 사용한다. 해당 방향의 프로젝트가 없으면 링크와 빈 행을 생략한다.

| 현재 프로젝트  | 이전 링크와 목적지                                     | 다음 링크와 목적지                                             |

| Lorekeeper     | `이전 프로젝트 · ILOG` — `/projects/ilog/`             | `다음 프로젝트 · Matching SSAFY` — `/projects/matching-ssafy/` |
| Matching SSAFY | `이전 프로젝트 · Lorekeeper` — `/projects/lorekeeper/` | 없음                                                           |

외부 링크의 새 탭 이동과 hover·focus는 기존 [TextLink 규칙](components.md#textlink와-비조작-요소)을 따른다. 이전·다음 프로젝트는 같은 탭에서 대상 상세의 맨 위로 이동하고 주 제목에 포커스를 둔다. 상단 `포트폴리오로`의 목적지는 `/#projects`로 유지한다.

## 반영 대상

- 디자인 문서: [프로젝트 상세](pages/project-detail.md)의 본문 섹션과 목차, 외부 링크 배치, 하단 이동, 마지막 프로젝트 처리와 검토 기준을 수정하고 관련 문서의 상충 규칙을 정리했다.
- Pencil: [portfolio.pen](../pen/portfolio.pen)의 세 상세 화면과 각 1440/390px 변형에 공통 본문 섹션과 링크·이동 변경을 반영했다. 마지막 프로젝트에는 Lorekeeper로 돌아가는 이전 링크만 남겼다.

## 수용 기준

- 세 프로젝트의 두 화면 크기에서 `프로젝트 개요 / 아키텍처 / 문제 해결 / 결과`가 같은 순서로 나타나고, 큰 섹션 제목과 개별 사례 소제목이 구별된다. 데스크톱 목차의 항목·순서가 본문과 일치한다.
- 기존 색상·글꼴·목차·링크·태그 스타일이 유지되고, 기능 묶음·시스템 도식·문제와 해결·결과 요약을 각 섹션에서 구별할 수 있다. 모바일에서도 도식과 정보 묶음의 글자가 잘리거나 가로로 넘치지 않아야 한다.
- 세 프로젝트의 두 화면 크기에서 외부 링크가 소개 영역에 한 번씩 나타나며 본문 하단에는 프로젝트 이동만 남는다.
- Lorekeeper의 두 저장소를 레이블로 구분할 수 있다.
- 첫·가운데·마지막 프로젝트의 이동 구성이 설계 표와 일치하고, `코드에서 확인하기`와 하단 `프로젝트 목록으로`가 없다.
- 링크의 44px 조작 영역, 기존 TextLink 원본 참조와 스타일 변수를 유지한다. 본문 재구성 시 확인된 사실·담당 범위·검증 한계를 보존한다. 링크 추가·제거 뒤 겹침·잘림·불필요한 빈 행이 없어야 한다.
- 디자인 문서와 Pencil의 문구·배치·목적지를 대조하고, 1440/390px 실제 렌더를 확인한다. 이 항목은 디자인 Deliverable #25의 검토 기준이다. 후속 Deliverable #34의 코드·브라우저 검증은 별도 웹 검증 기록으로 확인한다.
