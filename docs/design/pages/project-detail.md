### 프로젝트 개요

일기와 일상을 기록하고 감정 분석 결과를 확인하는 서비스입니다. 인증·사용자·그룹·API Gateway 네 서비스를 단독 설계하고 구현했습니다.

**주요 기능**

- 일기 작성과 감정 분석 결과 확인
- 그룹을 통한 기록 공유
- Google 소셜 로그인

**담당 범위**

- 로그인과 토큰 발급·재발급, 로그아웃
- 내 정보 조회와 사용자 프로필 관리
- 그룹 생성·조회, 초대 코드와 그룹 참여
- 서비스 라우팅과 공통 인증 처리

### 아키텍처

API Gateway가 서비스별 요청을 전달하고 쿠키의 액세스 토큰을 공개 키로 검증합니다. Auth Service는 Google 로그인과 토큰 발급을 맡습니다. User·Group Service는 Gateway가 전달한 사용자 식별자를 사용해 요청을 처리합니다.

네 서비스는 제가 담당했습니다. 일기·미디어와 AI 기능은 서비스 전체 구성에 포함되지만 이 도식은 제가 구현한 인증·사용자·그룹 요청 흐름에 집중합니다.

#### 도식 명세

도식 제목은 `인증과 내부 서비스 요청 흐름`이다. 구성 요소는 브라우저, API Gateway, Auth Service, User Service, Group Service, Google이다. Gateway·Auth·User·Group에 `담당` 레이블을 붙인다. 선은 논리적인 요청 관계를 나타내며 번호가 있는 전체 로그인 시퀀스로 표현하지 않는다.

| 연결 | 선 레이블 | 근거 |
| --- | --- | --- |
| 브라우저 → API Gateway | 서비스 요청 | Gateway의 단일 진입점·라우팅 역할 |
| API Gateway → Auth Service | 로그인·토큰 처리 | 인증 경로 라우팅 |
| Auth Service ↔ Google | OIDC 로그인 | Google 사용자 정보 처리와 로그인 연결 |
| API Gateway → User Service | 검증된 사용자 식별자 | 내 정보 조회와 X-User-Id 전달 |
| API Gateway → Group Service | 검증된 사용자 식별자 | 그룹 기능과 X-User-Id 전달 |

Gateway 설명은 `토큰 검증 · 공통 인증 · 라우팅`이다. Auth의 토큰 발급과 Gateway의 검증을 같은 단계로 합치지 않는다. 내부 서비스 접근을 네트워크 수준에서 차단했다는 주장은 자료에 없어 넣지 않는다.

### 문제 해결

#### 로그인 후 내 정보 조회가 다시 로그인으로 돌아가던 문제

**문제**

Google 로그인 이후 내 정보를 조회하면 User Service가 다시 로그인 화면으로 돌려보냈습니다.

**원인**

Gateway와 내부 서비스가 서로 다른 인증 방식을 적용하고 있었습니다. User Service의 폼 로그인과 세션 인증이 Gateway에서 검증한 요청을 그대로 처리하지 못했습니다.

**해결**

각 서비스에서 인증 객체를 생성하는 방법과 Gateway에서 공통 처리하는 방법을 검토했습니다. Gateway가 쿠키의 액세스 토큰을 공개 키로 검증하고 `X-User-Id` 헤더로 사용자 식별자를 전달하도록 했습니다. User Service의 폼 로그인과 세션 인증을 비활성화하고, User·Group Service가 검증된 식별자를 사용하도록 인증 경계를 정리했습니다.

#### Google 로그인에서 사용자 정보 처리가 실행되지 않던 문제

**문제**

Google 로그인 후 기존 사용자 정보 처리 코드가 호출되지 않았습니다.

**원인**

Google은 OIDC 방식으로 동작해 일반 OAuth2 사용자 정보 처리와 실행 경로가 달랐습니다.

**해결**

`OidcUserService` 기반으로 사용자 정보 처리를 변경해 정보 저장과 로그인 성공 후 JWT 발급을 연결했습니다.

#### 로그인 후 내부 서비스 주소로 이동하던 문제

**문제**

로그인 후 브라우저가 내부 주소인 `auth-ms`로 이동했습니다.

**원인**

Gateway가 Auth Service로 요청을 전달하면서 Host 헤더가 내부 서비스 주소로 바뀌었습니다.

**해결**

인증 경로에 `PreserveHostHeader` 필터를 적용해 외부 요청의 Host를 유지했습니다.

### 결과

**Google 로그인 동작 확인**

수정 후 Google 로그인의 정상 동작을 직접 확인했습니다.

**인증 예외 처리 확인**

Gateway 테스트에서 인증 예외 경로, 토큰 누락과 비유효 토큰 처리를 확인했습니다.

**검증 범위**

유효 토큰의 Gateway 통과 테스트는 비활성화된 상태였습니다. Jenkins·EC2 배포와 운영은 담당하지 않았습니다.

**회고 — 서비스 규모에 맞는 선택**

팀에서는 프로젝트 규모에 비해 MSA가 과하다는 의견이 있었습니다. 저는 인증 서비스와 Gateway를 직접 구현해 보는 방향을 제안했습니다. 프로젝트를 마친 뒤에는 기술적 도전과 함께 팀과 서비스 규모에 맞는 선택인지 검토해야 한다는 점을 배웠습니다.

#### 편집 근거

세 장애의 상황·원인·해결과 인증 테스트의 한계는 ILOG 기록의 `구현 과정에서 해결한 문제`와 `검증`에 근거한다. 회고의 제안과 실제 구현 구성을 구별한다. 2026-09-11 기록의 최종 합의 범위인 인증·팀(그룹)을 실제 구현한 네 서비스 전체와 같은 뜻으로 쓰지 않는다. 프론트엔드 병행 사실은 기록에 있지만 구체적 화면은 미확인이라 새 담당 화면을 추가하지 않는다.

## Lorekeeper

- 경로: `/projects/lorekeeper/`
- 기간: `2026.05 — 진행 중`
- 역할: `로그인·작품·회차`
- 기여 요약: `로그인 프론트엔드·백엔드 / Work·Episode 백엔드 개발`
- 기술 태그: `Spring Boot`, `OAuth2`, `JPA`

팀 규모는 자료에 없어 표시하지 않는다.

### 프로젝트 개요

장편 창작자가 작품별 회차와 세계관을 관리하고 설정 오류 탐지 결과를 확인하는 서비스입니다. 로그인 프론트엔드·백엔드와 작품·회차 API를 개발하고 있습니다. AI 설정 오류 탐지 엔진은 제 담당 범위에 포함하지 않습니다.

**주요 기능**

- 작품과 회차 원고 관리
- 세계관과 설정 오류 탐지 결과 확인
- Google 로그인

**담당 범위**

- 로그인 화면과 반환 처리, 보호된 화면 접근 제어
- 토큰 발급·재발급, 쿠키 인증과 CSRF 처리
- 작품 생성·조회·제목 수정과 사용자별 접근 처리
- 회차 상태·원고 관리, 다운로드와 여러 회차 업로드

### 아키텍처

Next.js 프론트엔드와 Spring Boot API 서버를 연결합니다. PostgreSQL은 사용자·작품·회차 데이터를 저장하고, Redis는 OAuth 요청과 인증 토큰 데이터를 관리합니다.

현재 계층형 구조로 MVP를 먼저 구현하고 있습니다. 서비스 분리는 이후 계획이며, 지금 여러 도메인을 독립 서비스로 분리한 상태는 아닙니다.

#### 도식 명세

도식 제목은 `로그인·작품·회차의 구성`이다. Next.js 프론트엔드, Spring Boot 백엔드, PostgreSQL, Redis를 배치한다. 프론트엔드에는 `로그인 담당`, 백엔드에는 `로그인·Work·Episode 담당`을 붙여 애플리케이션 전체를 본인이 만들었다고 오해하지 않게 한다. 백엔드 내부 도메인을 독립 서버 상자로 그리지 않는다.

| 연결 | 선 레이블 | 근거 |
| --- | --- | --- |
| Next.js 프론트엔드 ↔ Spring Boot 백엔드 | 로그인·작품·회차 API | 기록의 프론트엔드·백엔드 역할과 담당 API |
| Spring Boot 백엔드 ↔ PostgreSQL | 사용자·작품·회차 데이터 | 시스템 구성의 관계형 데이터 저장 역할 |
| Spring Boot 백엔드 ↔ Redis | OAuth 요청·토큰 데이터 | 로그인 백엔드의 Redis 사용 |

이는 담당 기능을 중심으로 축약한 구성도다. Agent·Neo4j는 전체 서비스에 존재하지만 이번 도식에는 넣지 않고, 화면 본문에서 AI 엔진이 별도 담당임을 밝힌다. API와 저장소 사이의 관계를 표시하며 미확인 배포 토폴로지나 서비스 간 프로토콜을 추가하지 않는다.

### 문제 해결

#### 브라우저와 서버의 로그인 상태 맞추기

**구현 과제**

로그인 반환 처리부터 보호된 화면 접근과 로그아웃까지, 브라우저 상태와 서버의 인증 처리를 함께 연결해야 했습니다.

**구현**

프론트엔드에서는 Google OAuth 로그인 화면과 반환 처리, 보호된 화면 접근 제어를 구현했습니다. 서버에서는 JWT 발급·재발급, Redis 기반 OAuth 요청과 리프레시 토큰 관리, 쿠키 인증과 CSRF 처리를 맡았습니다. 로그아웃 이후 브라우저 상태와 현재 사용자 정보도 함께 동기화했습니다.

#### 작품 접근과 여러 회차 원고 처리

**구현 과제**

작품별 접근을 처리하고, 여러 회차의 원고 입력을 검증해 일괄 처리하는 기능이 필요했습니다.

**구현**

Work에서 작품 생성·조회·제목 수정과 사용자별 접근 처리를 구현했습니다. Episode에서는 회차 상태, 원고 수정·조회, UTF-8 다운로드와 여러 회차 업로드의 입력 검증·일괄 처리를 구현했습니다.

### 결과

**로그인 흐름 구현**

로그인 프론트엔드·백엔드와 로그아웃 이후의 인증 상태 동기화를 구현했습니다.

**작품·회차 API와 테스트 작성**

Work·Episode API와 도메인 테스트를 작성했습니다. 프로젝트는 현재 개발 중입니다.

**검증 범위**

여기에는 구현과 테스트 작성까지 확인된 범위를 기록했습니다. 현재 전체 테스트 통과나 운영 성과를 의미하지 않습니다.

**회고 — MVP 구현을 먼저 진행**

ILOG에서 서비스 규모에 맞는 기술 선택의 중요성을 배운 뒤, Lorekeeper에서는 계층형 MVP를 먼저 구현하고 이후 서비스를 분리하는 순서로 바꿨습니다. 서비스 분리는 향후 계획입니다.

#### 편집 근거

두 사례는 Lorekeeper 기록의 로그인·Work·Episode 담당 범위에 근거한 구현 과제다. 장애 발생이나 성능 개선을 확인한 기록은 없어 `원인 / 장애 해결`로 꾸미지 않는다. MVP와 회고는 2026-09-10 사용자 설명에 근거한다. AI 엔진·세계관 처리·애플리케이션 전체 구현을 개인 기여로 확장하지 않는다.

## Matching SSAFY

- 경로: `/projects/matching-ssafy/`
- 기간: `2025.07 — 2025.08`
- 역할: `팀·실시간 채팅`
- 기여 요약: `6인 팀 · 백엔드 팀·채팅 도메인`
- 기술 태그: `Spring Boot`, `WebSocket`, `STOMP`

### 프로젝트 개요

SSAFY 교육생의 프로젝트 팀 구성을 지원하는 서비스입니다. 팀 생성·조회·수정·삭제와 초대·참여 요청·거절·탈퇴, 팀 상태 잠금 기능을 개발했습니다. 팀 채팅과 1:1 채팅도 담당했습니다.

**주요 기능**

- 팀 탐색과 팀원 초대·참여 요청
- 팀 구성 상태 관리
- 팀 채팅과 1:1 채팅

**담당 범위**

- 팀 관리와 초대·참여·거절·탈퇴 처리
- 팀 상태 잠금
- 실시간 메시지 송수신과 채팅방·기록 조회 API
- 프론트엔드 채팅 연동과 팀·채팅 테스트 작성

### 아키텍처

React 화면과 Spring Boot 백엔드를 연결했습니다. 팀 관리와 채팅방·메시지 기록 조회는 API로 제공하고, 실시간 메시지는 WebSocket과 STOMP로 송수신합니다.

저는 백엔드의 팀·채팅 도메인과 프론트엔드 채팅 연동을 담당했습니다. 아래 도식은 API 조회와 실시간 메시지 전달이라는 두 흐름을 구분합니다.

#### 도식 명세

도식 제목은 `팀·채팅 API와 실시간 메시지`다. React 화면과 Spring Boot 백엔드를 배치하고, 사이에 아래 두 종류의 연결을 별도로 표시한다. 백엔드 안의 팀·채팅은 기능 영역이며 독립 서비스가 아니다. 백엔드에는 `팀·채팅 담당`, 화면 쪽 연결에는 `채팅 연동 담당`을 붙인다.

| 연결 | 선 레이블 | 근거 |
| --- | --- | --- |
| React 화면 ↔ Spring Boot 백엔드 | 팀·채팅방·기록 조회 API | 팀 도메인과 채팅방·메시지 기록 API, 프론트엔드 연동 |
| React 화면 ↔ Spring Boot 백엔드 | WebSocket · STOMP 메시지 | 실시간 채팅 구현과 프론트엔드 WebSocket 연동 |

PostgreSQL 사용은 기술 기록에 있지만 채팅 영속화의 구체적 저장 구조는 이번 자료에 정의되지 않았다. 도식은 요청 흐름으로 한정하고 테이블 구조·메시지 브로커·확장 구성을 추정하지 않는다.

### 문제 해결

#### 팀 구성 단계의 여러 동작 처리

**구현 과제**

팀 생성 이후에도 초대·참여 요청·거절·탈퇴와 팀 상태 잠금 등 팀 구성 과정의 여러 동작을 처리해야 했습니다.

**구현**

팀 관리 API와 초대·참여·거절·탈퇴 처리를 구현했습니다. 팀장이 팀에서 나갈 때의 팀 처리 로직도 수정했습니다.

#### 채팅 연결과 1:1 채팅 상태 연동

**문제**

프론트엔드 채팅 화면을 연결하는 과정에서 WebSocket 연결·CORS 설정 오류와 1:1 채팅 상태 처리 문제가 있었습니다.

**해결**

WebSocket 연결과 CORS 설정을 수정하고 1:1 채팅 상태 처리를 프론트엔드와 맞췄습니다. 팀·1:1 메시지 송수신과 채팅방 생성·메시지 기록 조회 API를 연동했습니다.

### 결과

**팀·채팅 기능 구현과 연동**

팀 관리 API, 팀·1:1 실시간 채팅과 채팅방·메시지 기록 조회를 구현했습니다. 프론트엔드 연동 과정에서 연결과 채팅 상태 처리를 수정했습니다.

**단위·통합 테스트 작성**

팀 서비스·컨트롤러와 채팅방·메시지·멤버 서비스의 단위 테스트 및 통합 테스트를 작성했습니다.

**검증 범위**

이번 기록은 구현·연동 수정과 테스트 작성 범위입니다. 현재 전체 테스트 통과나 동시 접속 성능을 측정한 결과는 포함하지 않습니다.

#### 편집 근거

기능과 수정·테스트 작성은 Matching SSAFY 기록의 담당 범위와 연동 기록에 근거한다. CORS 오류의 세부 원인과 팀장 탈퇴 시 적용한 정확한 규칙은 기록에 없어 추가하지 않는다. 별도 회고가 확인되지 않아 회고 문단을 만들지 않는다.

## 배치와 시각적 위계

[공통 규칙](../foundations.md)의 배경·글꼴·색상·두 열 구성을 유지한다. 1440px에서는 왼쪽 소개 448px, 간격 128px, 오른쪽 본문 608px이며 상단·좌우 여백은 기존 96/128px다. 1024px 미만에서는 단일 열로 전환하고, 390px 본문 폭은 좌우 24px를 제외한 342px다. 320px에서는 같은 여백 안의 272px에 맞춘다.

왼쪽은 `포트폴리오로`, 프로젝트명, 기간, 역할·기여 요약, 네 항목 목차, 외부 링크 순서다. 오른쪽은 개요부터 결과까지 하나의 문서 흐름으로 읽는다. 왼쪽과 개요 본문의 역할을 구별해 왼쪽에는 짧은 담당 요약, 개요에는 실제 담당 기능을 둔다. 모바일은 소개와 외부 링크 뒤 64px를 띄우고 본문을 시작하며 상세 목차는 표시하지 않는다.

다음 값은 기존 체계에 맞춘 시작값이며 Pencil에서 실제 줄바꿈과 도식 레이블을 보고 조정한다. 조정 결과는 이 문서와 공통 요소 명세에 반영한다. 색상과 서체를 새로운 테마로 바꾸지 않는다.

| 요소 | 데스크톱 | 모바일 | 역할 |
| --- | --- | --- | --- |
| 큰 섹션 제목 | 24px, 굵기 600, 주 제목색 | 22px | 네 섹션의 경계를 먼저 찾게 한다. |
| 사례·기능 묶음 제목 | 18px, 굵기 600, 주 제목색 | 18px | 큰 섹션 안에서 개별 이야기를 구별한다. |
| 본문 | 16px, 행간 1.8, 본문색 | 동일 | 기존 가독성을 유지한다. |
| 문제·원인·해결 등의 레이블 | 13px, 굵기 600, 주 제목색 | 동일 | 설명의 종류를 색에만 의존하지 않고 구별한다. |
| 큰 섹션 사이 | 80px | 64px | 본문 소제목 사이 간격보다 크게 둔다. |
| 큰 제목과 내용 사이 | 24px | 24px | 제목에 속하는 첫 내용을 분명히 한다. |
| 사례 사이 | 32px | 32px | 서로 다른 문제를 한 문단으로 읽지 않게 한다. |
| 레이블과 설명 사이 | 8px | 8px | 설명의 소속을 유지한다. |

첫 섹션을 제외한 큰 섹션은 상단에 기존 구분선 색의 1px 선을 두고 24px 뒤에 제목을 배치한다. 줄은 본문 폭만큼이며 섹션 앞 여백에 더해 문서 전체가 과도하게 길어지면 앞 여백 안에서 조정한다. 전체 섹션을 각각 큰 배경 카드로 감싸지 않는다.

### 프로젝트 개요 표현

짧은 소개 아래 주요 기능과 담당 범위를 소제목·목록으로 구분하고 마지막에 기존 SkillTag 세 개를 둔다. 소개 1개 문단, 기능 3개, 담당 범위 4개라는 이 문서의 실제 내용을 사용한다. 기능·담당 목록은 세로로 배치하고 줄바꿈한 항목은 텍스트 시작선을 맞춘다. 기술 태그는 간격 8px로 배치하며 본문 폭을 넘으면 다음 행으로 옮긴다. 태그를 버튼처럼 강조하거나 클릭 효과를 추가하지 않는다.

### 아키텍처 표현

[SystemDiagram](../components.md#systemdiagram)으로 정적 구성도와 연결 레이블을 표현한다. 도식 제목과 `담당` 범례, 도식, 위에 정의한 설명 문단 순서다. 제작용 `도식 명세` 표 자체를 화면에 옮기지 않는다. 선의 방향과 레이블은 프로젝트별 표가 기준이며 설명할 연결을 보기 좋게 만들기 위해 바꾸지 않는다.

도식은 본문 폭을 사용하고 높이는 내용에 맞춘다. 내부 여백은 데스크톱 24px·모바일 16px, 노드 간 최소 간격은 16px로 시작한다. 노드 제목은 14px, 보조 역할과 선 레이블은 13px로 읽으며 모바일에서도 축소하지 않는다. 담당 노드는 기존 청록색 선과 `담당` 레이블, 나머지는 기존 구분선 색으로 구별한다. 레이블을 삭제한 색상 구분만 사용하지 않는다.

- ILOG 데스크톱: 브라우저와 Gateway를 위아래에 두고 아래에 Auth·User·Group 세 갈래를 둔다. Google은 Auth 아래에 두어 인증 관계를 다른 서비스 관계와 구별한다. 좁은 화면에서는 Gateway 아래에 `인증 / 사용자 / 그룹` 경로를 세로로 쌓고 각각의 시작·목적지를 레이블로 명시한다. 같은 Gateway를 세 경로의 시작 표시로 반복해도 세 개의 Gateway 인스턴스처럼 표현하지 않는다.
- Lorekeeper 데스크톱: Frontend와 Backend를 위아래에 두고 Backend 아래 PostgreSQL·Redis를 두 갈래로 배치한다. 모바일에서는 저장소 연결을 세로로 쌓는다. 도메인 이름을 독립 서비스로 그리지 않는다.
- Matching SSAFY: React와 Spring Boot 사이에 `API 조회 / 실시간 메시지` 두 경로를 별도 행으로 표시한다. 모바일에서는 두 행을 각각 세로 흐름으로 배치하고 역할 레이블을 유지한다.

도식에는 드래그·확대 버튼·실행 애니메이션·hover를 추가하지 않는다. 페이지 자체의 기존 커서 조명은 유지하되 도식에 새로운 포인터 효과를 주지 않는다. 서비스 스크린샷을 임의로 생성하지 않는다.

### 문제 해결 표현

[ChallengeBlock](../components.md#challengeblock)을 사례별로 반복한다. 제목 아래 레이블과 본문을 세로로 두고 다음 사례까지 32px를 띄운다. 사례 제목과 본문은 같은 왼쪽 정렬을 유지한다. 사례 사이에는 1px 구분선을 사용하며 제목마다 아이콘이나 큰 번호를 추가하지 않는다.

ILOG는 `문제 / 원인 / 해결` 세 부분을 제공한다. Lorekeeper 두 사례와 Matching SSAFY의 팀 관리 사례는 실제 장애 기록이 아닌 구현 과제이므로 `구현 과제 / 구현`으로 표시한다. Matching SSAFY 채팅 사례는 확인된 `문제 / 해결`만 둔다. 없는 원인 레이블이나 빈 설명 칸을 만들지 않는다. 기술명은 본문에 넣고 문단 전체를 코드 블록으로 표시하지 않는다.

### 결과 표현

[ResultItem](../components.md#resultitem)으로 핵심 결과 제목과 설명을 묶는다. 두 결과는 데스크톱에서 2열·간격 16px로, 모바일에서 한 열로 배치한다. 각 묶음은 투명 배경과 기존 구분선 색의 1px 테두리, 6px 모서리, 16px 내부 여백을 사용한다. 결과 제목은 18px, 설명은 기존 16px다. hover나 버튼 동작은 없다. 두 열의 높이는 더 긴 내용에 맞추되 텍스트를 자르지 않는다.

세 프로젝트 모두 확인된 성과 수치가 없어 이 문서의 짧은 결과 제목을 사용한다. 임의의 퍼센트·성능·완료율을 큰 숫자로 만들지 않는다. 검증 범위는 두 결과 아래 24px 간격의 일반 본문으로 두고, 회고가 있는 ILOG·Lorekeeper는 그 아래 소제목과 문단을 배치한다. Matching SSAFY에는 빈 회고 영역을 만들지 않는다.

## 읽기와 이동 반응

데스크톱 목차는 아래 순서와 각 큰 섹션 제목에 대응한다. hash가 없으면 프로젝트 개요를 선택하고, 마지막 섹션에서 문서 끝에 도달하면 결과를 선택한다. 도식·사례 소제목을 독립적인 목차 항목으로 추가하지 않는다.

| 앵커 | 목차와 본문 큰 제목 |
| --- | --- |
| `#overview` | 프로젝트 개요 |
| `#architecture` | 아키텍처 |
| `#challenges` | 문제 해결 |
| `#results` | 결과 |

기존 코드의 `#scope / #implementation / #verification` 세 앵커는 새 설계의 기준이 아니다. 코드 반영 시 기존 직접 링크의 호환 처리를 함께 검토한다. 이 문서 작업에서 기존 웹의 앵커 동작을 변경했다고 간주하지 않는다.

커서 조명은 [홈 규칙](home.md#커서-조명), 목차의 이동·활성 판정·중단·포커스·history는 [홈 탐색](home.md#목차와-스크롤)을 재사용한다. 큰 섹션의 앵커가 제목에 도착하도록 연결한다. 데스크톱 앵커 여백은 96px, 모바일은 80px를 유지한다. 모바일의 큰 제목·소제목은 본문 흐름 안에 두고 고정하지 않는다. 숨긴 상세 목차는 Tab 순서에도 남지 않는다.

하단의 `코드에서 확인하기`와 저장소별 코드 확인 링크, 마지막 프로젝트의 `프로젝트 목록으로`는 제거한다. 양 끝을 순환하지 않는다. 각 링크는 기존 TextLink의 44px 조작 영역과 상태를 사용하며 긴 링크 문구는 자연스럽게 줄바꿈한다.

이전·다음은 같은 탭에서 대상 상세의 맨 위로 이동하고 프로젝트 주 제목에 포커스를 둔다. 브라우저 뒤로·앞으로는 기존 위치 복원을 유지한다. 페이지를 떠나면 이전 조명·목차 관찰·지연된 포커스 처리를 정리한다. 새 링크에 별도 로딩·전환 효과를 추가하지 않는다.

## 문서·시안 검토 기준

- 세 프로젝트의 1440/390px 화면에 네 섹션과 각 프로젝트의 실제 콘텐츠가 같은 순서로 있고, 목차·큰 제목·사례 제목의 위계가 일치한다.
- 기능과 담당 범위, 시스템 도식, 문제와 해결, 결과와 검증 한계를 각각 구별할 수 있다. 제작용 도식 표·편집 근거가 화면 본문에 나오지 않는다.
- ILOG의 네 담당 서비스, Lorekeeper의 부분 담당과 현재 MVP, Matching SSAFY의 API와 실시간 흐름을 도식에서 구별한다. 도식의 작은 글자를 읽기 위해 이미지를 확대해야 하면 재배치한다.
- 기존 색상·서체·목차·링크·태그의 스타일과 원본 참조를 유지한다. 도식·결과·사례 요소가 링크처럼 보이거나 hover 반응을 갖지 않는다.
- 390px에서 긴 제목·도식·태그·결과·링크가 겹치거나 잘리지 않는다. 320px은 설계의 추가 검토 폭이며 Pencil 필수 시안은 1440/390px이다.
- 네 외부 주소가 해당 프로젝트의 소개 영역에 한 번씩 있고, 첫·중간·마지막 프로젝트의 하단 이동이 표와 일치한다.
- 공통 요소 수정 시 홈·전체 열람·A4 시안의 사용처 영향을 확인한다. PDF의 기존 네 장 구성과 문구를 이번 상세 재구성에 맞춰 자동 변경하지 않는다.
- Work #29에서 실제 프레임과 렌더를 확인하고, Work #32에서 문서·시안의 최종 차이를 보완해 검증 근거를 남긴다. 문서 검토를 렌더 검증으로 보고하지 않는다.

### 구현 이후 반응 검토

네 앵커의 직접 진입과 목차 클릭, 연속 이동·휠 개입·페이지 이탈, 뒤로·앞으로·새로고침을 마우스·키보드·터치에서 확인한다. 이전·다음 이동 후에는 대상 주 제목에 포커스가 있고 다음 Tab이 자연스럽게 이어져야 한다. 모바일에서 숨긴 목차가 포커스 대상에 남지 않아야 한다. 움직임 줄이기·기존 커서 조명·TextLink 상태의 규칙도 대조한다. 이 항목들은 후속 웹 구현의 검증이며 이번 디자인 Work의 완료 근거에 포함하지 않는다.
