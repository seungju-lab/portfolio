# 프로젝트 상세

세 프로젝트를 같은 읽기 화면으로 제공한다. 경로는 홈에서 정의한다. 넓은 화면은 왼쪽 프로젝트명·기간·역할·목차와 오른쪽 본문, 좁은 화면은 단일 열이다. 홈으로 돌아가는 링크와 저장소 링크가 필요하다. 제목 크기를 제외한 본문 규칙은 [공통 규칙](../foundations.md)을 따른다.

## ILOG

기간 2025.10 — 2025.11, 6인 팀. 인증·사용자·그룹·API Gateway 네 서비스를 단독 설계·구현했다. 저장소는 `https://github.com/ju1115/ilog`다.

### 서비스와 담당 범위

일기와 일상을 기록하고 감정 분석 결과를 확인하는 서비스입니다. 저는 Java와 Spring Boot로 인증·사용자·그룹·API Gateway를 단독 설계하고 구현했습니다. 로그인과 토큰 발급, 사용자 조회, 그룹 초대·참여, 서비스 라우팅과 공통 인증을 맡았습니다.

### 로그인했는데 다시 로그인으로 돌아간 이유

Google 로그인 이후 내 정보를 조회하면 User Service가 다시 로그인 화면으로 돌려보냈습니다. Gateway와 내부 서비스가 서로 다른 인증 방식을 적용하고 있었습니다. Gateway에서 쿠키의 액세스 토큰을 공개 키로 검증하고 X-User-Id 헤더로 사용자 식별자를 전달했습니다. User Service의 폼 로그인과 세션 인증을 비활성화하고, User·Group Service가 검증된 식별자를 사용하도록 정리했습니다.

### Google 로그인 흐름을 연결한 과정

Google은 OIDC 방식으로 동작해 기존 OAuth2 사용자 정보 처리 코드가 호출되지 않았습니다. OidcUserService를 사용해 사용자 정보 저장과 JWT 발급을 연결했습니다. 로그인 후 내부 주소인 auth-ms로 이동하던 문제는 Gateway의 PreserveHostHeader 필터로 외부 요청의 Host를 유지해 수정했습니다.

### 확인한 결과와 남은 범위

Google 로그인 정상 동작을 직접 확인했습니다. Gateway 테스트에서는 인증 예외 경로와 토큰 누락·비유효 토큰 처리를 확인했습니다. 유효 토큰의 Gateway 통과 테스트는 비활성화된 상태였습니다. Jenkins·EC2 배포와 운영은 담당하지 않았습니다.

### 서비스 분리에 대한 회고

팀에서는 프로젝트 규모에 비해 MSA가 과하다는 의견이 있었습니다. 저는 인증 서비스와 Gateway를 직접 구현해 보는 방향을 제안했습니다. 구현을 마친 뒤에는 기술적 도전뿐 아니라 팀과 서비스 규모에 맞는 선택인지 함께 검토해야 한다는 점을 배웠습니다.

## Lorekeeper

기간 2026.05 — 진행 중. 로그인 프론트엔드·백엔드, Work·Episode 백엔드 개발. 저장소는 `https://github.com/soma-lorekeeper/lorekeeper-backend`, 프론트엔드는 같은 조직의 `lorekeeper-frontend`다. 팀 규모는 미확인으로 표시하지 않는다.

### 서비스와 담당 범위

장편 창작자가 작품별 회차와 세계관을 관리하고 설정 오류 탐지 결과를 확인하는 서비스입니다. 저는 로그인 프론트엔드·백엔드와 작품·회차 API를 개발하고 있습니다. AI 설정 오류 탐지 엔진은 제 담당 범위에 포함하지 않습니다.

### 브라우저와 서버의 로그인 상태 연결

Google OAuth 로그인 화면과 반환 처리, 보호된 화면 접근 제어를 구현했습니다. 서버에서는 JWT 발급·재발급, Redis 기반 OAuth 요청과 리프레시 토큰 관리, 쿠키 인증과 CSRF 처리를 맡았습니다. 로그아웃 이후 브라우저 상태와 현재 사용자 정보도 함께 동기화했습니다.

### 작품과 회차를 다루는 API

Work에서는 작품 생성·조회·제목 수정과 사용자별 접근 처리를 구현했습니다. Episode에서는 회차 상태, 원고 수정·조회, UTF-8 다운로드와 여러 회차 업로드의 입력 검증·일괄 처리를 구현했습니다.

### 진행 상황과 테스트

현재 개발을 진행하고 있으며, Work·Episode 도메인 테스트를 작성했습니다. 작품 접근과 회차 처리 규칙을 API 구현과 함께 다루고 있습니다.

## Matching SSAFY

기간 2025.07 — 2025.08, 6인 팀. 백엔드 팀·채팅 도메인 담당. 저장소는 `https://github.com/ju1115/Matching_SSAFY`다.

### 서비스와 담당 범위

SSAFY 교육생의 프로젝트 팀 구성을 지원하는 서비스입니다. 저는 팀 생성·조회·수정·삭제, 초대·참여 요청·거절·탈퇴와 팀 상태 잠금 기능을 개발했습니다. 팀 채팅과 1:1 채팅도 담당했습니다.

### 실시간 메시지와 기록 조회

WebSocket과 STOMP로 팀·1:1 채팅 메시지를 송수신하고, 채팅방 생성과 메시지 기록 조회 API를 구현했습니다. 프론트엔드의 WebSocket 연결과 채팅 화면을 연동하며 연결·CORS 설정 오류, 1:1 채팅 상태 처리를 수정했습니다.

### 테스트와 검증 범위

팀 서비스·컨트롤러와 채팅방·메시지·멤버 서비스의 단위 테스트 및 통합 테스트를 작성했습니다. 프론트엔드 연동 과정에서는 WebSocket 연결과 1:1 채팅 상태 처리를 수정했습니다.

## 표현과 검토

편집 근거: Lorekeeper와 Matching SSAFY는 테스트 작성까지 확인된 범위다. 이번 디자인 작업에서 테스트를 재실행하지 않았다. 전체 테스트 통과·운영 성과·동시 접속 성능을 추가하지 않는다. Matching SSAFY의 CORS 오류 세부 원인은 기록에 없어 추정하지 않는다. 이 편집 메모는 화면 본문에 넣지 않는다.

각 소제목 다음에 문단을 두고, 중요한 기술명은 본문 안에 자연스럽게 넣는다. 본문을 도해·근거 카드로 다시 포장하지 않는다. 외부 저장소와 다음 프로젝트 링크는 끝에 배치한다. 검증 한계는 `확인한 결과` 문단에서 읽을 수 있게 유지한다.

1440/390px에서 프로젝트명·담당 범위·본문 순서·뒤로 이동이 명확해야 한다. 긴 한글 제목은 두 줄 이상 자연스럽게 허용한다. 실제 웹의 목차 이동과 링크 성공 여부는 아래 기준으로 구현 이후 확인한다.

## 읽기와 이동 반응

왼쪽에는 `담당 범위 / 구현 과정 / 검증과 회고` 목차를 둔다. 본문 문장을 바꾸지 않고 아래 묶음에 앵커를 부여한다. 각 묶음은 다음 앵커 전까지의 문단을 포함한다.

| 앵커              | ILOG                                     | Lorekeeper                         | Matching SSAFY            |
| ----------------- | ---------------------------------------- | ---------------------------------- | ------------------------- |
| `#scope`          | 서비스와 담당 범위                       | 서비스와 담당 범위                 | 서비스와 담당 범위        |
| `#implementation` | 로그인했는데 다시 로그인으로 돌아간 이유 | 브라우저와 서버의 로그인 상태 연결 | 실시간 메시지와 기록 조회 |
| `#verification`   | 확인한 결과와 남은 범위                  | 진행 상황과 테스트                 | 테스트와 검증 범위        |

ILOG의 `서비스 분리에 대한 회고`는 검증과 회고 묶음에 포함한다. Lorekeeper와 Matching SSAFY에는 새로운 회고 내용을 만들어 넣지 않는다. hash가 없으면 담당 범위를 선택하고, 마지막 묶음에서 문서가 끝나면 검증과 회고를 선택한다.

커서 조명은 [홈 규칙](home.md#커서-조명), 목차의 이동·활성 판정·중단·포커스·history는 [홈 탐색](home.md#목차와-스크롤)을 재사용한다. 모바일에서는 상세 목차를 숨기고 소제목은 본문 흐름에 둔다. 홈의 모바일 고정 소제목은 상세의 긴 한글 제목에 적용하지 않는다. 직접 앵커 진입의 모바일 여백 80px는 그대로 유지한다.

`홈으로`는 `/#projects`로 이동해 프로젝트 목록을 보여 준다. 브라우저 뒤로 가기는 기존 위치 복원을 유지한다. 본문 끝의 다음 프로젝트는 ILOG→Lorekeeper→Matching SSAFY 순서이며, 마지막에는 `프로젝트 목록으로`를 둔다. 다음 프로젝트는 새 상세의 맨 위로 이동하고 주 제목에 포커스를 둔다. 저장소 링크는 [TextLink](../components.md#textlink와-비조작-요소)의 외부 이동 규칙을 따른다. 페이지를 떠나면 이전 조명·목차 관찰·지연된 포커스 처리를 정리한다.

### 반응 검토 기준

세 상세 경로와 각 앵커로 직접 진입해 제목·문단 순서·선택 목차를 확인한다. ILOG의 검증 목차가 회고만 건너뛰어 가리키지 않아야 한다. 목차 이동 중 홈으로 나가도 뒤늦은 스크롤·포커스가 새 화면에 적용되지 않아야 한다. 다음 프로젝트·홈·브라우저 뒤로 이동을 마우스와 키보드로 확인하고, 모바일에서는 숨긴 목차가 Tab 순서에 남지 않아야 한다. 움직임 줄이기의 조명·전환 규칙도 동일하게 적용되어야 한다.
